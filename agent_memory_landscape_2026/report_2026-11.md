# Memorable: Code Audit, memorable.sh, and the Agent Memory Landscape (Nov 2026)

**Date:** 2026-11-14
**Scope:** (A) what memorable-ai's memory structure actually is today, (B) what the YC company memorable.sh is doing, (C) research, papers and startups from 2025 to Nov 2026, (D) what we should build.
**Supersedes:** the May 2026 [report.md](report.md) for strategy. Its gap matrix is still accurate on conversational memory.

---

## TL;DR

1. **memorable-ai today stores facts about users and nothing else.** It has one flat `memories` table (fact / preference / skill / rule / context), plus raw conversation logs and an in-process graph that is lost on restart. There is no procedural memory (how a task gets done) and no episodic retrieval (what happened in past runs). The "skill" type holds regex matches like *"I can…"* about the user, not agent skills.
2. **The headline feature doesn't work with current SDKs.** I checked against the installed openai 2.30 and anthropic 0.102: the OpenAI and Anthropic hooks never attach, because `OpenAI.chat` and `Anthropic.messages` are per-instance `cached_property` attributes. Only `litellm.completion` is intercepted. On the default sync path, the Mem0-style update pipeline, the summary and the graph update are also skipped. The full list of defects is in §A4.
3. **memorable.sh (YC) builds procedural memory for coding agents.** It records an agent's tool-call trace, turns it into a workflow with dead ends removed, merges shared steps into a graph, and on a similar task injects a pointer of roughly 50–300 tokens. Its claims: 19–40% fewer turns or tool calls and 98% less context than a skill file. It is backed by Garry Tan's gbrain/gstack ecosystem. **It has the same name as this project.**
4. **Conversational-memory benchmarks are saturated.** Top systems score 92–95% on LoCoMo and LongMemEval (all self-reported). Our only measurement is 40% on a 10-question subset. Catching up is necessary, but it won't set us apart.
5. **The field has moved to memory that changes what an agent does,** and procedural memory is the most active area: AWM → ReasoningBank → ACE → Procedural Graphs → TraceCompiler / ReTrace, plus Anthropic's "dreaming" (Nov 6, 2026). Evaluation is moving to task success per dollar (MERIT, MemoryArena, DolphinBench).
6. **Recommendation:** fix the foundation first (2–3 weeks). Then make memorable-ai an **open-source, SQL-first experience memory**: facts, episodes and procedures in one store, with verifiable procedures, provenance, and action-based evaluations. The interceptor already sees every tool call. It is a trace-capture point that memorable.sh has to build hooks for, harness by harness. Settle the name question before investing in a brand.

## Part A — What memorable-ai actually is (code audit)

### A1. Memory structure as implemented

```
                       ┌───────────────────────── WRITE PATH ─────────────────────────┐
LLM call ─► Interceptor ─► summary refresh* ─► MemoryExtractor ─► MemoryUpdater* ─► Storage ─► GraphBuilder*
             (litellm only)   (LLM, 3-5 sent.)   pattern regex +     ADD/UPDATE/        SQL        NetworkX
                                                  LLM JSON extract    DELETE/NOOP                   (in-memory)
                                                                     (* skipped on the default sync path)

                       ┌───────────────────────── READ PATH ──────────────────────────┐
LLM call ─► Interceptor ─► Mode (auto | conscious | hybrid) ─► HybridRetriever.retrieve(last user msg)
                                                               ├─ semantic: cosine over ≤1000 JSON embeddings (Python loop)
                                                               ├─ FTS5 / LIKE
                                                               ├─ BM25 (index rebuilt per query over ≤1000 rows)
                                                               ├─ entity overlap (capitalized-word regex)
                                                               └─ graph (2-hop NetworkX)
                                                               ─► weighted sum of raw scores ─► top-10
                                                               ─► prepended {"role":"system"} "Relevant memories: - [type] text"

BACKGROUND: MemoryConsolidator every 6h → importance = f(old score, access, recency, type); negation-word contradiction check
```

**Tables** ([storage.py](../memorable_ai/core/storage.py)):

| Table | Holds | Notes |
|---|---|---|
| `memories` | `content`, `memory_type`, `namespace`, `embedding` (JSON), `importance_score`, `access_count`, `valid_from` / `valid_to` / `invalidated_at` / `superseded_by_id`, `confidence`, `session_id`, `extra_metadata` | The only memory that gets retrieved. No vector index. |
| `conversations` | raw `messages`, `response`, `extracted_memories`, `summary` | Write-only log. Never retrieved, so it isn't really episodic memory. |
| `memories_fts` | SQLite FTS5 mirror | SQLite only, and not updated when a memory's content changes |
| (graph) | NetworkX `MultiDiGraph` in process memory | Not persisted. Optional Neo4j wrapper. |

**Memory types in cognitive terms:**

| Type | Present? | What exists |
|---|---|---|
| Working | Partial | Injected system message. In "conscious" mode it is cached once per session. |
| Semantic (facts about the user and world) | **Yes, this is the whole product** | `memories` rows |
| Episodic (what happened, when, with what outcome) | **No** | `conversations` is logged but never searched or summarized into episodes |
| Procedural (how to do X: steps, tools, conditions) | **No** | None. `memory_type="skill"` holds user statements ("I can…") |
| Temporal validity | Schema only | Columns exist, but UPDATE overwrites in place and DELETE hard-deletes (§A4) |

### A2. Write path details

- **Extraction** ([extraction.py](../memorable_ai/core/extraction.py)): only the latest user message plus the assistant response are used. Pattern mode is regex ("I am…", "X lives in…", "Always…", "Currently…"). LLM mode asks for a JSON array of `{content, type, dia_ids}` with the rolling summary as context. No session date is passed, so relative dates can't be resolved. This is the root cause the May LOCOMO diagnosis found.
- **Update** ([update.py](../memorable_ai/core/update.py)): a Mem0-paper ADD/UPDATE/DELETE/NOOP call per fact, against the top-10 similar memories.
- **Dedup on insert:** an exact `ilike` match, then a scan of *all* same-type rows for substring overlap with more than 80% word overlap.

### A3. Read path details

- The query is the raw last user message. There is no query rewriting, no reranker, and no temporal filter.
- Fusion adds `weight × raw_score` across signals ([retrieval.py:293-324](../memorable_ai/core/retrieval.py#L293-L324)).

### A4. Verified defects, ranked by impact

| # | Defect | Evidence | Impact |
|---|---|---|---|
| 1 | **OpenAI and Anthropic hooks never attach.** `hasattr(OpenAI.chat, "completions")` is `False`, because `chat` is a `cached_property`. Anthropic has the same problem. The hook fails silently. | Run against the installed SDKs. [interceptor.py:60-96](../memorable_ai/core/interceptor.py#L60-L96). The integration test only checks that *some* hook registered, and LiteLLM satisfies that. | The zero-code claim works only for `litellm.completion`, and only when it is called as a module attribute after `enable()`. Async clients, streaming, the Responses API and `acompletion` are never covered. |
| 2 | **Anthropic calls would get `{"role":"system"}` injected into `messages`** | [memory_engine.py:291](../memorable_ai/core/memory_engine.py#L291) | Anthropic's API returns a 400 for that role. Once #1 is fixed, every Anthropic call would fail. The context has to go in the `system` parameter. |
| 3 | **The default sync write path bypasses the pipeline.** With no running event loop (a typical script), `_store_conversation_sync` calls `store_memories` directly. | [memory_engine.py:468-517](../memorable_ai/core/memory_engine.py#L468-L517) | The interceptor flow never runs the summary, the ADD/UPDATE/DELETE update phase, or the graph update. |
| 4 | **The injection path has no user scoping.** `retrieve()` doesn't pass `user_id` to any signal, and BM25 and entity search can't accept one. | [retrieval.py:62-120](../memorable_ai/core/retrieval.py#L62-L120) | Within a namespace, user A's memories get injected into user B's prompts. This is a privacy bug. |
| 5 | **Fusion is dominated by BM25.** Cosine scores fall in [0,1] while raw BM25 scores are unbounded (often 2–15). | [retrieval.py:317-321](../memorable_ai/core/retrieval.py#L317-L321) | Semantic weight has almost no effect. The standard fix is reciprocal rank fusion (RRF) or per-signal normalization. |
| 6 | **The temporal model isn't honored.** DELETE hard-deletes. UPDATE overwrites `content` in place (the `invalidate_superseded` flag is ignored) and doesn't re-embed or update FTS. | [update.py:105-112](../memorable_ai/core/update.py#L105-L112), [storage.py:554](../memorable_ai/core/storage.py#L554) | No history, so the bi-temporal claim is false. An updated row's embedding still describes the *old* content. |
| 7 | **Graph retrieval is effectively dead.** Newly ADDed facts carry no `id`, so no memory node gets created. `find_related` returns only memory nodes. The graph is in process memory and lost on restart. Entities are any capitalized word, including "The" and "My". | [builder.py:63-90](../memorable_ai/graph/builder.py#L63-L90), [update.py:113-116](../memorable_ai/core/update.py#L113-L116) | The "graph for multi-hop" claim isn't functional. |
| 8 | **Neo4j query precedence bug:** `WHERE a OR b AND valid` | [neo4j_backend.py:75-76](../memorable_ai/graph/neo4j_backend.py#L75-L76) | Invalidated edges are returned whenever the first clause matches. It also matches only the first query token. |
| 9 | **Scale ceilings.** Semantic search loads the 1000 highest-*importance* rows into Python. BM25 is rebuilt on every query. Dedup scans every same-type row on every insert. | [retrieval.py:210-216](../memorable_ai/core/retrieval.py#L210-L216), [storage.py:275](../memorable_ai/core/storage.py#L275) | Past about 1000 memories, new low-importance facts can't be found semantically. Inserts are O(n²) overall. |
| 10 | **The updater loads a SentenceTransformer per fact,** because `HybridRetriever(...)` is constructed inside `_find_similar` | [update.py:61-67](../memorable_ai/core/update.py#L61-L67) | Seconds of latency per extracted fact |
| 11 | **Summaries bleed across sessions.** `get_summary` ignores its key and returns the latest summary in the namespace. `store_summary` writes to the latest row. | [summary.py:75-82](../memorable_ai/core/summary.py#L75-L82) | One user's summary gets used for another user's extraction. |
| 12 | **Postgres scoping breaks.** `json_extract` is SQLite/MySQL syntax. Identity aliases live in memory only. The session-ID fallback is an md5 of the first user message. | [storage.py:210-222](../memorable_ai/core/storage.py#L210-L222) | The README advertises Postgres, Neon and Supabase. |
| 13 | **The consolidator's access bonus is always 0.** It reads `metadata.access_count`, but the counter is a column. Contradiction detection groups memories by their first three words. | [consolidation.py:125](../memorable_ai/core/consolidation.py#L125) | Importance reduces to recency × type weight. |

**Evaluation status:** LOCOMO has been run on 1 conversation × 10 questions. The best judge score is 40% (with dated context), retrieval-only scores 80%, and the oracle scores 60% ([STATUS.md](../ResearchDoc/STATUS.md)). The harness ingests raw turns and doesn't exercise the production extraction and update pipeline.

**Bottom line:** the architecture diagram in the README is correct in shape. The implementation is alpha quality in exactly the places that are meant to differentiate it: the interceptor, the temporal model and the graph.

## Part B — memorable.sh (YC): "graph procedural memory for AI agents"

**Sources:** [YC launch](https://www.ycombinator.com/launches/U2j-memorable-graph-procedural-memory-for-ai-agents-stop-re-teaching-your-agents), [memorable.sh](https://memorable.sh), [docs](https://memorable.sh/docs), [demo video](https://youtu.be/3m9I1zHSMPk)

### B1. Who

- **Nikhil Krishnaswamy**, Stanford CS. Built an iOS MCP at AGI Inc and has published at COLM and IEEE.
- **Advaiyt Sane**, CMU CS. Built Nvidia dev tools that generate about 50k AV tests a month.
- The site says it is YC-backed. Testimonials come from Garry Tan and Kulveer (a YC visiting partner).

### B2. What and how

The problem they describe: agents re-derive the same workflow on every similar task, and existing memory layers store facts, not procedures. Their pitch is *"Memorable turns agent reasoning into a graph search problem… Imagine a world where your agents don't reason."*

| Layer | Behavior (from site and docs) |
|---|---|
| **Traces** | Records prompt, tool calls, files read, commands, results and exit codes, in order. Captured through `npx memorable-cli` hooks (Claude Code, Codex, Cursor, OpenCode, Devin, Antigravity), a Claude connector, or `POST /v1/extract {session_id, task_description, harness, tool_calls[]}` |
| **Workflow synthesis** | "Removes dead ends and keeps the sequence of steps that reached the goal." The parse is deterministic: the same trace gives the same steps. |
| **Procedure schema** | `title`, `schema_version`, `steps[] {seq, action, activity_class, command, repeat_count}`, `postconditions[]`, `embedding`. Steps carry preconditions, postconditions, a verify command and real exit codes. Targets are named "by what it is about" so they survive tool changes. |
| **Graph assembly** | "Shared steps and prefixes reveal new paths." Composes workflows and learns implicit skills. Chained plans return "an ordered plan of procedures" and name any gap. |
| **Retrieval** | Exact, then lexical, then vector. About 60 ms per prompt. |
| **Injection** | A short pointer of about 50–100 tokens in the launch copy (293 tokens in the gstack example). Rendering is "guarded, injection-safe". |
| **Storage and privacy** | A local file, the user's gbrain database, or QM Postgres. "Only the prompt and allow-listed tool arguments leave the machine". Embeddings are computed server-side. Write consent is fail-closed, and `disable` makes memory read-only. |
| **Multi-agent** | "A procedure one agent recorded is recalled by every other agent on the same store." There is also a read-only MCP server with 5 tools. |

### B3. Claimed results (self-reported, small fixtures)

| Setting | Claim |
|---|---|
| gbrain + Claude Code (3-bug coding fixture, 454 runs) | 16 → 13 turns per task (−19%) |
| Quartermaster + Codex (3 replications) | 5 → 3 tool calls (−40%); pass rate 80% → 91% |
| OpenHome | Task completion 70% → 100% |
| gstack `/investigate` | 293 tokens vs 15,593 for the skill file (−98% context) |
| Launch copy | "60% fewer tool calls, 40% lower latency" |

### B4. Assessment

**Strengths:**
- **The wedge is sharp.** Coding agents produce structured, verifiable traces (commands and exit codes), so postconditions can be checked automatically.
- **Distribution:** they are embedded in Garry Tan's gbrain/gstack ecosystem and in YC's Quartermaster.
- **The ROI story is concrete:** fewer tool calls and fewer tokens.
- **The privacy posture fits enterprises:** local stores and allow-listed arguments.

**Weaknesses and open questions:**
- The evidence comes from tiny fixtures (3 bugs, 5 tool calls).
- **Staleness and invalidation aren't documented.** What happens when the repo or an API changes?
- **Retrieval precision at scale is a known failure mode.** [Demystifying Agent Skills](https://arxiv.org/abs/2608.14036) found actual-use precision falls from 29.6% to 3.3% as a skill pool grows from 5 to 100.
- **"Agents don't reason" overclaims.** [ReTrace](https://arxiv.org/abs/2611.14492) found planner-free workflows trail full agents by 3–5 points of success, while running 100× faster.
- Embeddings are computed server-side, and the CLI is closed, so this is not truly self-hosted.

**Competitive overlap with memorable-ai today: low.** They store *how*; we store *what about the user*. The overlap becomes high if we move into procedural memory, which Part D recommends, so positioning has to be deliberate.

### B5. The name collision

A YC-backed company now operates as **Memorable** in exactly our category (agent memory) at memorable.sh. Our package is `memorable-ai` and the README brand is "Memorable". Expect search, SEO and mindshare confusion, and possibly a trademark conflict depending on filings. I haven't searched trademark registries, and none of this is legal advice. **Decide before investing further in the brand:** rename (cheap now, expensive later), or keep the name with a clearly distinct product positioning.

## Part C — The landscape, Nov 2026

### C1. The taxonomy has converged

- **Cognitive framing:** *semantic* (what is known), *episodic* (what happened), *procedural* (how to do it). Mem0's 2026 report names procedural memory as the third type and says tooling for it is "still early-stage" ([Mem0, State of AI Agent Memory 2026](https://mem0.ai/blog/state-of-ai-agent-memory-2026)).
- **Systems framing:** Anthropic's Nov 6, 2026 post *The components of agent memory* ([anthropic.com/engineering](https://www.anthropic.com/engineering/components-of-agent-memory)) describes a four-level hierarchy: **transcripts → memory notes → memory representations (wikis) → injected context**. An offline "dreaming" pass moves information between levels and validates notes against transcripts, which are treated as ground truth.

### C2. Conversational memory is saturated and converging

| System | LoCoMo | LongMemEval | Mechanism | Source |
|---|---|---|---|---|
| Mem0 (Apr 2026 algorithm) | 92.5 | 94.4 | Single-pass ADD-only extraction; semantic + BM25 + entity fusion; entity linking replaced the graph store; ~6.9k tokens/query | [Mem0](https://mem0.ai/blog/state-of-ai-agent-memory-2026) |
| Mastra Observational Memory | — | 94.87 (gpt-5-mini) | Observer and Reflector background agents write a dated, append-only observation log; no vector DB; prompt-cache friendly; ~30k context | [Mastra](https://mastra.ai/research/observational-memory) |
| Hindsight (Vectorize) | 92.0 | 94.6 | Four networks (world facts, experiences, entity summaries, opinions); retain/recall/reflect; parallel semantic + BM25 + graph + temporal, then cross-encoder rerank; Postgres + pgvector | [arXiv 2512.12818](https://arxiv.org/html/2512.12818v1) |
| Agent Zero Memory | 93.6 | 95.6 | Provenance-aware long-term memory | [arXiv 2608.29606](https://arxiv.org/pdf/2608.29606) |
| Zep / Graphiti | ~80–83 | 71.2 | Bi-temporal knowledge graph | [Mem0 table](https://mem0.ai/blog/state-of-ai-agent-memory-2026) |
| Letta (filesystem) | 74.0 | — | Plain file tools | same |
| **memorable-ai** | **40% (10-question subset)** | not run | — | [STATUS.md](../ResearchDoc/STATUS.md) |

All of these are vendor self-reports. Judge model, retrieval depth and recall-only vs end-to-end grading all move the numbers. Hindsight argues that naive full-context dumping is competitive on both benchmarks, which means they are close to saturated ([Hindsight manifesto](https://hindsight.vectorize.io/blog/2026/03/23/agent-memory-benchmark)).

**The recipe has converged:** LLM extraction at write time, session-date anchoring, multi-signal retrieval (semantic + BM25 + entity + temporal), cross-encoder rerank, and update-on-write. All of it is reproducible. None of it sets anyone apart anymore.

### C3. Evaluation now measures what agents do

| Benchmark / study | Finding that matters for us |
|---|---|
| **MERIT**, *When Does Memory Help?* ([2609.05441](https://arxiv.org/abs/2609.05441), Jul 2026) | Memory takes dependent tool tasks from 0.00 to 0.55–1.00 success. **Agents act on a correctly retrieved value only 55% of the time.** Embedding retrieval is unreliable for updated facts (0.30–0.95), while update-on-write fact stores hold 0.70–1.00. **Hybrid is worse than the fact store alone.** Swapping implementations moves success by up to 60 points. Full replay is never economical. Benchmark and traces are open. |
| **MemoryArena** ([2602.16313](https://arxiv.org/abs/2602.16313), ICML 2026) | Systems near-saturated on LoCoMo fail on interdependent multi-session tasks (57 steps on average, traces over 40k tokens). |
| **DolphinBench, STATE-Bench** (Mem0) | 600 tasks testing whether memory improves actions, plus whether agents improve from earlier workflow experience. |
| **BEAM** | Scores fall from 64.1 at 1M tokens to 48.6 at 10M (Mem0). Temporal abstraction at scale is unsolved. |

### C5. Consolidation, or "dreaming", is now standard

- **Anthropic (Nov 2026):** stored notes are validated against transcripts. Results reported: CL-Bench mean reward went from 0.655 to 0.838 with memory (Opus 5.5). Wiki-only answers on 25 questions rose from 13% to 48% after 128 dreaming sessions. Wiki plus search reached 61%, against 53% for search alone, and saved about 20k tokens per question. A failures-only memory rule *hurt* (−0.15 to −0.23). Their recommendations: describe the *purpose* of memory, not the procedure; keep the injected layer small and use an index; one writer per page; watch for bloat (one wiki reached 1.77× the size of its corpus).
- **gbrain** (Garry Tan): markdown in git is the source of truth, Postgres/PGLite is a rebuildable index (HNSW + BM25 merged with RRF, plus backlink boost), a RESOLVER.md skill dispatcher, and a 9-phase nightly maintenance cycle.
- **Mastra:** the Observer and Reflector agents described in C2.
- **Hindsight:** the "reflect" operation writes opinions and observations.

### C6. Learned memory policies

- **Memory-R1** ([ACL 2026](https://preview.aclanthology.org/ingest-acl/2026.acl-long.583/)): an RL-trained Memory Manager (ADD/UPDATE/DELETE/NOOP) plus an Answer Agent. 152 training QA pairs gave +68.9% F1 over Mem0 on LLaMA-3.1-8B.
- **Mem-α** ([2509.25911](https://huggingface.co/papers/2509.25911)): RL-learned memory construction. Trained on 30k tokens, it generalizes past 400k. A tuned Qwen3-4B beats gpt-4.1-mini.
- **MemEvolve** (ICML 2026): co-evolves the memory representation and the retrieval policy.
- **Implication:** our ADD/UPDATE/DELETE prompt is a policy that could later be trained on our own action-based evaluations. That is a research angle for the paper.

### C7. Security: memory is an attack surface

- **MemoryGraft** ([2512.16962](https://arxiv.org/pdf/2512.16962)): a single poisoned "experience" persists across sessions and is triggered by semantic similarity. This applies directly to procedural memory: a poisoned procedure gets replayed.
- **Laundering attacks** ([2606.24322](https://www.emergentmind.com/papers/2606.24322)): untrusted content enters through the agent's own summaries, through tool echoes, or through manufactured corroboration. Up to 68% attack success against existing defenses.
- **Defenses:** *provenance-derived* trust rather than content-inferred trust, plus taint propagation ([2606.22030](https://arxiv.org/pdf/2606.22030)). OWASP lists memory poisoning as **ASI06**.
- **Implication:** every memory and procedure needs `source` (user / assistant / tool / web), trust tier and lineage columns from day one.

## Part D — What we can do

### D1. Strategic options

| Option | Description | Verdict |
|---|---|---|
| **A. Mem0-style user memory library** | Fix bugs and chase LoCoMo and LongMemEval | ❌ as the headline. The market is saturated, hyperscalers bundle it, and we start at 40% on 10 questions. Still do the cheap catch-up (D3, Phase 0–1), because facts are required context for procedures. |
| **B. Clone memorable.sh** | Procedural memory for coding-agent CLIs | ❌ head-on. They have distribution through gbrain, gstack and QM, plus the YC network and a working CLI. |
| **C. Open-source, SQL-first experience memory** | One store for **facts + episodes + procedures**, with verifiable procedures, provenance, and action-based evaluations. Python-native for agent *frameworks* (OpenAI Agents SDK, LangGraph, CrewAI, AutoGen, LiteLLM) rather than coding CLIs. | ✅ **Recommended** |

**Why C can win:**
1. **We already sit on the trace stream.** Once fixed, the interceptor sees every `tool_calls` / `tool_use` block and every tool result inside `messages`. memorable.sh has to write hooks for each harness. We capture traces automatically from any framework that calls an LLM SDK.
2. **Open source and self-hosted** (memorable.sh computes embeddings server-side and ships a closed CLI). Enterprises with agent workloads on their own Postgres want this.
3. **Facts parameterize procedures.** "This user deploys with pnpm to Fly.io" fills a procedure's bindings. Neither memorable.sh (procedures only) nor Mem0 (facts only) joins the two.
4. **Verifiability and safety as features:** postconditions checked in SQL, provenance and trust tiers, abstention under low precision, git-like history of procedures.
5. **Research credibility:** an action-based evaluation paper (MERIT / MemoryArena / τ²-bench) is publishable. A LoCoMo paper at 40% is not.

### D2. Target memory model

```
┌──────────────────────── Memorable store (Postgres + pgvector | SQLite + sqlite-vec) ────────────────────────┐
│ L0 transcripts   conversations / tool events (append-only, ground truth for dreaming + provenance)           │
│ L1 episodes      task, trajectory ref, outcome (pass/fail + evidence), cost (tokens, $, tool calls, latency) │
│ L2 semantic      facts with bi-temporal validity, entity links, provenance, trust tier                       │
│ L3 procedural    procedures (graph): steps, pre/postconditions, bindings, success stats, versions            │
│ L4 injected      tiny index (~100–300 tokens): top facts + matched procedure pointer + "verify" step         │
└──────────────────────────────────────────────────────────────────────────────────────────────────────────────┘
        ▲ capture: interceptor (sync, async, streaming, Responses API) · record_trace() API · MCP server
        ▼ consolidate ("dream"): nightly LLM pass validated against L0; merge shared prefixes; invalidate stale
```

**Procedural tables (sketch):**

```sql
procedures(id, namespace, title, intent_signature, intent_embedding, version, status /*active|stale|quarantined*/,
           success_count, failure_count, avg_tool_calls, avg_tokens, last_verified_at,
           source /*trace|human|imported*/, trust_tier, created_from_episode_id, superseded_by_id)
procedure_steps(id, procedure_id, seq, action, tool_name, arg_template_json,
                bindings_json /*constant|user_input|copied_output|transform|llm_decision*/,
                precondition, postcondition, verify_cmd, optional bool)
procedure_edges(src_step_id, dst_step_id, kind /*next|depends_on_value|branch_on|alt_path*/,
                evidence_json, observed_count, success_rate)        -- graph assembly across procedures
procedure_runs(id, procedure_id, episode_id, matched_by /*exact|lexical|semantic*/, match_score,
               followed bool, outcome, tool_calls, tokens, latency_ms, deviation_step)
```

### D3. Roadmap

**Phase 0 — Make the existing product true (2–3 weeks)**
1. **Interceptor:** patch the *resource classes*. These are verified to exist in the installed SDKs:
   - `openai.resources.chat.completions.Completions.create` / `AsyncCompletions.create`
   - `openai.resources.responses.Responses.create`
   - `anthropic.resources.messages.Messages.create` / `AsyncMessages.create`
   - `litellm.completion` / `acompletion`

   Put Anthropic context into `system`. Handle streaming by buffering and storing on completion. Add a real integration test that asserts each SDK is wrapped.
2. Run the sync and async write paths through the same pipeline (summary, then extract, then update, then graph).
3. **User scoping on every signal,** with a portable JSON filter or a real `user_id` column. Persist identity aliases.
4. **RRF fusion** in place of the raw weighted sum. Add a cross-encoder rerank on the top 50.
5. **Temporal correctness:** UPDATE invalidates the old row and inserts a new one with `superseded_by_id`, a re-embedding and an FTS sync. DELETE invalidates instead of removing.
6. **Vector index:** pgvector or sqlite-vec. Build BM25 and embedder state once.
7. Persist the graph as SQL `entities` / `edges` tables, or drop it until it earns its place (Mem0 dropped its graph store too).
8. Key summaries by session. Load the embedder once.

**Phase 1 — Episodic layer and conversational table stakes (2 weeks)**
- Anchor session dates in extracted facts (the LOCOMO diagnosis R2/R3). Add an `episodes` table with outcome and cost.
- Run the **full LoCoMo (1,540 Q) + LongMemEval** as a regression gate only. A realistic target is 80%+, not leadership.

**Phase 2 — Procedural memory MVP (4–6 weeks)**
- **Capture:** turn tool-call sequences from the interceptor or `record_trace()` into episodes, with outcome labeled by explicit signal (exit code, test pass, user acceptance, or a judge).
- **Synthesize:**
  - Drop dead ends and retries using value attribution (TraceCompiler).
  - Extract preconditions from the agent's rationale text (ReTrace).
  - Classify bindings.
  - Refuse to compile when an irreversible side effect is under-determined.
- **Retrieve:** exact signature, then BM25, then embedding, then rerank, with a **precision gate**: abstain below threshold and log it. This is the 29.6% → 3.3% lesson. Inject the pointer plus the verify step, nothing more.
- **Learn:**
  - Keep per-procedure and per-edge success counters.
  - Store failure pitfalls (ReasoningBank).
  - Keep a graph edit only if replay or held-out success doesn't drop, and remember rejected edits (Procedural Graphs).
  - Mark a procedure stale after N postcondition failures.
- **Evaluate:**
  - **Metrics:** success, tool calls, tokens, $/task and latency, each with a memory-off control (MERIT-style).
  - **Suites:** τ²-bench and AppWorld subsets for procedural memory; MERIT (open source) for facts that change.
  - Publish the harness.

**Phase 3 — Dreaming / consolidation (2–3 weeks)**
- Replace the heuristic consolidator with an LLM pass that validates facts and procedures against L0 transcripts, merges shared prefixes into the graph, removes duplicates, and keeps the L4 injected index under budget. Model the cadence on Anthropic's guidance (focus on volatile information).

**Phase 4 — Provenance and safety (ongoing, design in from Phase 2)**
- Columns: `source`, `trust_tier`, lineage. Taint propagation through summaries. Quarantine procedures derived from untrusted tool output until they pass N verified runs. Human review in the CLI or dashboard.

**Phase 5 — Distribution**
- An MCP server (read and write), OpenAI Agents SDK and LangGraph adapters, and a `memorable dash` that shows procedures, runs and savings (memorable.sh's dashboard shows "runs where memory did not help" too; copy that honesty).

### D4. What not to do

- Don't headline LoCoMo numbers. Use them as regression tests.
- Don't build or require a graph database. A graph modeled in SQL tables is enough. Mem0 removed its external graph store.
- Don't claim that "agents don't reason". Deterministic replay costs 3–5 points of success (ReTrace). Position procedures as *guidance with verification*, with a fallback to full reasoning.
- Don't store failures only (Anthropic: −0.15 to −0.23). Store both, with outcome labels.
- Don't inject large playbooks. Keep injected context under about 300 tokens, with links to depth.

### D5. Decisions only the owner can make

1. **Name:** rename, or keep "Memorable" alongside a YC company with the same name in the same category?
2. **Target user:** agent *framework* builders in Python (recommended), coding-agent CLIs (memorable.sh's turf), or consumer chat apps (hyperscaler turf)?
3. **Business model:** pure open source and a paper, or open core with a hosted dashboard?
